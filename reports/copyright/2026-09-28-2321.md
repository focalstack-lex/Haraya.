This is a technical compliance review, not legal advice. Items marked **(jurisdictional)** depend on how Philippine
law applies to Haraya's business model and should be confirmed with counsel. Items marked **(objective)** are
verifiable technical defects.

Primary jurisdiction assumed: the Philippines (Davao Region users and businesses), so the Data Privacy Act of 2012
(RA 10173) and the Internet Transactions Act of 2023 (RA 11967) are the reference points rather than GDPR or CCPA.

## Lens 1: Intellectual property and trademark

**[P2] OpenStreetMap attribution is incomplete** (objective)
- `src/components/map/DavaoCoffeeMap.tsx:71-72`: `attribution: 'OpenStreetMap contributors'`.
- OSM data is licensed under ODbL, which requires the credit "© OpenStreetMap contributors" linked to
  `https://www.openstreetmap.org/copyright`. The copyright symbol and link are missing.
- Fix: set the attribution to `&copy; <a href="https://www.openstreetmap.org/copyright">OpenStreetMap</a> contributors`.

**[P2] Production use of the public OSM tile server** (objective, policy)
- `src/components/map/DavaoCoffeeMap.tsx:71`: tiles from `https://{s}.tile.openstreetmap.org`.
- The OpenStreetMap Foundation tile usage policy does not allow heavy production traffic on its community servers
  and can block apps that do. A live site should use a tile provider it has an account with (for example MapTiler,
  Stadia Maps or Thunderforest, each with free tiers) and credit it too.

**[P3] Unused legacy mascot images are publicly deployed**
- `public/mascot/aya-clay3d.jpg`, `aya-coffee-cup.jpg`, `aya-monoline.jpg`, `aya-portrait-canvas.jpg`,
  `aya-portrait-white.jpg`. Nothing in `src` references them since the official mascot replaced them, but Vite
  copies `public/` into the build, so they are reachable at `/mascot/*.jpg`.
- They show an earlier, off-model Aya of unrecorded origin. Remove them, or record where they came from and who
  holds the rights.

**[P3] Domain and email claims to confirm**
- `src/components/auth/AuthView.tsx:223` hint: "haraya.ph/#/roastery/your-handle".
- `src/services/authService.ts:68` seeded account `admin@haraya.ph`.
- If Haraya does not own `haraya.ph`, the hint tells roasters their storefront lives on a domain someone else may
  control. Use the real production domain.

**Passed**
- Brand, logo and mascot are Lex's own assets (`public/brand/`, `AyaMascot.tsx` drawn from the owner-supplied master).
- The demo dataset with Unsplash hotlinks was removed today; no third-party photo hotlinks remain in `src`.
- Third-party names (Google Maps, Google Calendar, Messenger, Viber) appear only as nominative references to the
  services users hand off to. No partner or endorsement claims.
- Plus Jakarta Sans is under the SIL Open Font License; Leaflet is BSD-2-Clause.

Score: **7/10**

## Lens 2: Accessibility (WCAG 2.1 AA)

**[P2] Modals do not manage focus** (objective)
- `src/components/common/FormControls.tsx:28-70` (`Modal`): Escape closes it and `aria-modal="true"` is set
  (`:70`), but focus is not moved into the dialog when it opens, not kept inside while it is open, and not returned
  to the triggering control on close.
- Keyboard and screen-reader users can tab into the page behind the sheet (WCAG 2.4.3 Focus Order).
  `WelcomeModal.tsx` has the same pattern.
- Fix: focus the first focusable element or the heading on open, trap Tab inside, and restore focus on close.

**[P3] Admin rejection note has no accessible name**
- `src/components/admin/AdminDashboard.tsx:141`: `<input>` with only a placeholder. Add `aria-label="Rejection note"`.

**[P3] 8px and 9px text in the Roaster dashboard**
- 7 occurrences of `text-[8px]` or `text-[9px]` (for example `src/components/roaster/RoasterDashboard.tsx:171-172`).
- This is not a WCAG failure by itself, but it is below comfortable reading size for chart labels and tooltips.
  Raise it to 11px or more.

**Passed (measured)**
- Every `<img>` has an `alt`; decorative ones use `alt=""`, and content images carry names.
- Every form field has an accessible name via `Field` (`FormControls.tsx:134` wraps it in `<label>`) or `aria-label`
  (search, city menus, mood input, flavor pins, sort and price selects).
- Contrast (WCAG 4.5:1): body `#594C3D` on linen 7.65:1; placeholder `#6E6150` on fill 4.72:1; link `#7D5C3D` on
  fill 4.75:1; cream on tan 4.62:1; closed `#8C3A2E` 7.49:1; open `#3E5C48` 6.83:1.
- `lang="en"` is set (`index.html:2`); focus rings are defined; reduced motion is respected; the map has a
  keyboard-usable venue list as an alternative.

Score: **8/10**

## Lens 3: Data privacy and security

**[P0] Government ID photos are stored in browser storage on a live site** (objective)
- `src/components/auth/AuthView.tsx:276-281` requires "One government ID (required)".
- `src/components/common/ImageUploadField.tsx:37` converts it to a data URL.
- `src/services/authService.ts:161-162` writes `permitDoc` and `idDoc` into the applications record in `localStorage`.
- A government ID is sensitive personal information under RA 10173. It sits unencrypted in the applicant's browser,
  where it is readable by any script on the origin, left behind on shared devices, and never reaches a reviewer
  (the admin screen `AdminDashboard.tsx:130-132` only shows it in the same browser). The UI hint admits "browser
  demo only", but the site is live.
- Fix now: stop requiring the ID upload until there is a secure intake (Supabase Storage in a private bucket, with
  a policy allowing only the owner and admins). Delete stored `idDoc` and `permitDoc` values from existing browsers.

**[P0] Passwords are stored in plain text in browser storage** (objective)
- `src/services/authService.ts:155` `credentials[email] = input.password`, checked by plain comparison at `:108`.
- Real users on a live site will reuse real passwords. Anyone with access to the device or any injected script can
  read them.
- Fix: move sign-in to Supabase Auth (already provisioned per `supabase/migrations/...:5-6`), and wipe
  `haraya_credentials` from browsers on load.

**[P0] Hardcoded admin credential in public source** (objective)
- `src/services/authService.ts:68` `admin@haraya.ph` and `:81` its password, shipped in the bundle.
- Anyone can sign in as admin. Today the effect stays in their own browser, but this becomes a real breach the
  moment admin actions touch Supabase. Remove it with the Supabase Auth move; admin role is granted in the database.

**[P0] Supabase: users can make themselves admin** (objective)
- `supabase/migrations/20260928000000_init_haraya_schema.sql:137`:
  `create policy "Users can update own profile" on public.profiles for update using (auth.uid() = id);`
- The policy has no `with check` and no column restriction, so a signed-in user can update their own `role` to
  `admin` and `status` to `approved` with the public anon key.
- Fix: revoke `update` on `role`, `status` and `cafe_profile_id` from `authenticated` (column privileges), or add
  `with check` so those columns must equal their old values. Only a service-role or admin-only function may change them.

**[P0] Supabase: any roaster can edit every cafe** (objective)
- `supabase/migrations/20260928000000_init_haraya_schema.sql:142-144`: the update policy checks only that the caller
  has role `roaster` or `admin`, not that the cafe is theirs.
- Fix: compare ownership, for example `exists (select 1 from profiles p where p.id = auth.uid() and (p.role = 'admin'
  or p.cafe_profile_id = cafes.id))`, and add a matching `with check`.

**[P1] No Privacy Policy or Terms of Service** (jurisdictional)
- There is no `/privacy` or `/terms` route and no footer link. A search for privacy, terms and consent across `src`
  finds nothing.
- Haraya collects personal information:
  - reservations: name and contact (`BeanReservationModal.tsx:75-79`)
  - roaster applications: name, email, password, permit number, ID photo
  - Cup Check photos and names
  - location on tap (`useLocation.ts:20`)
- RA 10173 requires a privacy notice stating what is collected, why, who receives it (the roaster for reservations),
  how long it is kept, and how to reach the data protection contact.
- Fix: add Privacy and Terms pages and link them in the footer and next to every form that collects personal data.

**[P2] No security headers** (objective)
- `vercel.json` defines only an SPA rewrite. There is no `Content-Security-Policy`, `X-Content-Type-Options`,
  `Referrer-Policy` or `Permissions-Policy` (HSTS is supplied by Vercel on its domains).
- Fix: add a `headers` block. The CSP must allow Google Fonts, the tile host, Open-Meteo and Supabase.

**[P2] Leaflet stylesheet from unpkg without integrity** (objective)
- `index.html:23`: `<link rel="stylesheet" href="https://unpkg.com/leaflet@1.9.4/dist/leaflet.css" />`, with no
  `integrity` attribute.
- A third-party CDN can change what loads. Leaflet is already an npm dependency, so import `leaflet/dist/leaflet.css`
  from the bundle instead.

**[P3] Google Fonts sends visitor IPs to Google**
- `index.html:18-22`. Mention it in the privacy notice, or self-host the font (the OFL allows it).

**Passed**
- No analytics, pixels or tracking cookies; storage is first-party `localStorage` for app state. No consent banner
  is required for what exists today.
- Location is requested only on tap and never stored (`useLocation.ts`); weather calls send fixed city coordinates,
  not the user's.
- `.env.local` is gitignored and untracked; `.env.example` holds placeholders only.
- The Supabase anon key being public is expected, which is why the two RLS findings above are P0.
- `bean_reservations` (which holds `user_phone`) has RLS on with no public policy, so phone numbers are not exposed.

**Upcoming, not yet in code:** the Aya assistant spec sends user chat text to DeepSeek. Before it launches, the
privacy notice must name DeepSeek as a processor, and the chat must say messages are processed by an AI provider.

Score: **2/10** (driven by the five P0s)

## Lens 4: E-commerce and consumer protection

**[P1] Seller identity and Haraya's role are not stated** (jurisdictional)
- The "Reserve or Inquire" flow (`BeanDropCard.tsx`, `BeanReservationModal.tsx`) collects buyer details and sends
  them to a roaster. Nowhere does it say that roasters are independent sellers, that Haraya is not party to the sale,
  or who to contact about a problem.
- RA 11967 places disclosure duties on online platforms that connect buyers and merchants. Whether Haraya counts as
  an e-marketplace under it is a question for counsel, but showing the roaster's registered business name and a
  "Sold and fulfilled by the roaster" line costs nothing.

**[P1] Reservations have no terms** (jurisdictional)
- Nothing says whether a reservation is binding, how payment and pickup work, or how to cancel. After submitting,
  the text only says the roaster "will reach out on the contact you left" (`BeanReservationModal.tsx:66`).
- Fix: add a short line above Send, such as "A reservation is a request. The roaster confirms price, payment and
  pickup with you directly," linked to Terms.

**[P2] User-generated content has no license, rules or takedown path**
- Cup Check posts accept photos and captions (`NewPostSheet.tsx`, `communityService.ts:71`).
- Terms should cover who owns the photos, the license granted to Haraya to display them, prohibited content, and how
  to report or remove a post. This is needed before posts move to Supabase and become public.

**[P3] "Verified" badge criteria are not explained**
- `CafeDetailModal.tsx:196-199` shows "Verified". Say what it means (for example "Business permit reviewed by
  Haraya") so it is not read as an endorsement of quality.

**Passed**
- The demo reviews, save counts and fabricated metrics were removed today. Ratings are personal and private;
  "Most saved" now reflects recorded saves only. No fake social proof remains.
- No subscriptions, auto-renewals or hidden fees exist.

Score: **5/10**

## Lens 7: Tax and financial transparency

**[P3] Prices do not state what they include or how payment works**
- Examples: `EditorialHero.tsx` "₱520 / bag" and `BeanDropCard.tsx` "/ bag, N in batch".
- State that prices are set by the roaster, and how payment happens (for example "Pay the roaster directly") in the
  reservation sheet.

**[P3] Habi link points to a local development address**
- `src/config/ecosystem.ts:6` `HABI_URL = 'http://127.0.0.1:5173'` is live in the header switcher. Visitors get a
  broken link to their own machine. Set the real URL or hide the switcher.

Score: **8/10**

## Remediation

Order of work:

1. **P0 now, on the live site**: remove the required ID upload, wipe `idDoc`, `permitDoc` and
   `haraya_credentials` from browsers, and fix the two RLS policies with a new migration. The admin credential and
   plain-text passwords go away with the move to Supabase Auth.
2. **P1**: Privacy and Terms pages with footer and form links; seller and reservation disclosure lines.
3. **P2 and P3**: focus management, OSM attribution and tile provider, security headers, bundled Leaflet CSS,
   purpose line on contact fields, UGC terms, and cleanup items.

Commands:

- `/copyright fix P0`: code and migration fixes that can be made without Supabase Auth (ID upload, storage wipe,
  RLS policies). The admin credential and password storage need the Auth migration and will be planned, not patched.
- `/copyright fix P1`: legal page scaffolds with bracketed placeholders for Lex and counsel to fill in (no legal
  text will be invented), plus disclosure lines.
- `/copyright fix all`: everything above.
